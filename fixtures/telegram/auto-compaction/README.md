# telegram/auto-compaction — M22 B1 automatic-compaction notice pin

**Card:** M22 Wave 1, B1 (compaction notice). Authored in Wave 0 as the
silence baseline; extended by B1 so the note is pinned end-to-end;
regenerated by Wave 2's B-card (frames now carry the B5 step transcript
in `Breadcrumb.steps` — the notice-once behaviour is unchanged).

**What it pins.** The AUTOMATIC compaction path in the runner's
`run_loop` (`should_compact(est_tokens)` → `compact()`), as distinct
from the `/compact` slash command `fixtures/telegram/slash-compact`
already pins. The `/compact` path confirms to the user; the automatic
path used to be **silent**. B1 closes that asymmetry: `run_loop` queues
a one-shot `history auto-compacted (N msgs -> M, ~Kk tokens)` notice on
`RunnerDeps::notices`, the next `TaskHud` drains it, and it rides the
first live HUD frame's summary — **exactly once** — then clears. This
fixture pins that: the note appears on precisely one outbound HUD
breadcrumb row and on no delivered chat text, no later frame, and no
other row.

**Shape.** Three plain-text telegram inbounds; the third turn opens with
one shell tool call so a live HUD frame actually posts (a pure-text turn
renders no frame — the drained note would be requeued for a later turn
and nothing here would pin it):

1. Inbound 1 → a ~760-char scripted reply.
2. Inbound 2 → another ~700-char reply. History now holds two exchanges.
3. Inbound 3 → `estimate_tokens(history)` (~467) exceeds the manifest's
   `compaction_soft_target_tokens: 300` (the replay twin of the
   production `COPPERCLAW_SOFT_COMPACTION_TARGET` env knob), so
   `run_loop` auto-compacts BEFORE the turn: it archives the transcript
   under the session's `outbox/_compactions/`, makes ONE summary-model
   provider call (the third scripted turn, `"SUMMARY: …"`), replaces the
   oldest half of history with a `compact_boundary` entry, and queues
   the B1 notice. The fourth scripted turn then opens with a `shell`
   tool call (`echo checking the timeline sketch`) — the HUD posts its
   first frame with the notice riding the summary — and the fifth turn
   answers inbound 3 against the compacted history.

The reply lengths are calibrated against the estimator
(`tokens = ceil(ws_collapsed_chars * 2/7)`): one exchange (~238 est
tokens) stays under the 300 target, two exchanges (~467) exceed it, so
compaction fires on exactly the third inbound. `model_rich_breadcrumbs`
is on so the HUD posts once and edits in place (the rich-adapter
modelling), matching the real Telegram surface.

**Assertions** (in `tests/replay.rs`, on top of the byte-stable JSONL
diff): the archive file exists (compaction genuinely ran), exactly five
provider requests arrived (three chat turns + one summarisation call +
one post-tool continuation), the post-compaction request's history
carries `compact_boundary: SUMMARY:`, and — the pin — the
`history auto-compacted` note appears on EXACTLY ONE outbound row (the
HUD frame that consumed it), never in delivered chat text, and never
twice.

**Regeneration.** `COPPERCLAW_M22W0_GENERATE=1 cargo test -p
copperclaw-host --test replay telegram_auto_compaction -- --nocapture`.
